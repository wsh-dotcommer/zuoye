## 1. 背景与目标

### 1.1 背景

团队成员每天需要耗费 15~30min 手工撰写日报，内容涵盖当日代码提交、任务进展及协作沟通情况。这一过程不仅重复低效，且常因遗忘导致信息缺失。

另外，团队 Leader 需要掌握成员的工作动态，但手工撰写的日报往往信息密度低、格式参差不齐，严重影响了阅读体验与管理效率。

本项目的原始团队把协作痕迹留在飞书（任务与群消息）和 GitHub（代码）两个平台上。本次复现按作业要求**只使用 GitHub 作为数据源**，因此把三类数据全部映射到 GitHub 的既有能力上：

| 日报板块 | 书中原始数据源 | 本期数据源（GitHub） |
| --- | --- | --- |
| 代码提交 | GitHub Commit | GitHub Commits API（含每条提交的变更统计） |
| 任务进展 | 飞书项目任务状态流转 | GitHub Issues 状态流转（新建 / 进行中 / 已完成）；v2.4 起额外接入飞书工作台任务的**状态快照**（已完成 / 进行中 / 未开始） |
| 协作沟通 | 飞书群消息 | GitHub PR 评审评论与 Issue 评论（关键词过滤） |
| 工时统计（v1.1） | 飞书考勤 API | GitHub 提交时间推导（无新增数据源） |

### 1.2 目标

构建一个自动化工具，旨在从团队现有的 GitHub 仓库中抓取当日工作数据，自动生成结构化日报，渲染为可直接发布的静态日报站，并精准推送给相关干系人。

### 1.3 目标用户

- 主要用户（数据生产者）：5 ~ 15 人的研发团队核心成员
- 主要读者（数据消费者）：团队 Leader 及项目经理
- 次要读者：团队外的项目干系人（通过静态日报站只读浏览）

## 2. 功能范围

### 2.1 做什么（本期）

#### 数据采集

- 对接 GitHub REST API，获取指定仓库在采集窗口内的 Commit 记录（含 Commit Message 与增删行数、变更文件数、变更文件名）
- 从 GitHub Issues 获取当日发生状态变更的任务列表（新建、进行中、已完成）
- 从 GitHub 的 PR 评审评论与 Issue 评论中提取与项目强相关的讨论记录，并按关键词白名单与敏感词黑名单过滤
- 采集窗口内的作者按配置的成员映射表归一到一个成员身份，实现按"人"聚合

#### 日报生成

- 将采集数据按"代码提交→任务进展→协作沟通"的逻辑进行编排
- 为每位团队成员生成独立的日报段落
- 输出 Markdown 格式（支持无缝转换为 HTML 邮件）与 HTML 格式
- 当日无任何记录的成员显示"今日无记录"；采集失败的数据源显示"数据获取失败"
- 条目可点击（v2.2）：提交行给短 SHA、任务行给 Issue 编号、协作沟通行给来源评论，均链接到 GitHub 对应页面
- 任务进展补上下文（v2.2）：标签、指派人与评论数；指派人与本段成员一致时不重复显示
- 单人团队合并标题（v2.2）：头部写 `- 团队：姓名（@username）` 承载成员身份，省略与之重复的成员标题

#### 趋势与对比（v2.3 新增）

- 头部新增两行：`对比上期（YYYY-MM-DD）：提交 ±N · 任务 ±N · 沟通 ±N · 工时 ±N.Nh` 与 `近 N 期：提交 ▁▂▃█（合计）· 工时 ▁▂▃█（合计）`
- 对比基数取"上一期已生成的日报"（不是严格的昨天：周末与节假日不生成日报，写死"昨天"会经常没有基准）；无历史时整行不出现
- 趋势行门槛（v2.4）：含当日在内的序列少于 3 期时整行不出现——两期合计容易被误读成"今天的数"，站点索引页的 SVG 趋势区块同步采用同一门槛
- 站点索引页新增"近 N 期趋势"区块：两张内联 SVG 柱状图（提交数、工时），标注日期与数值；不引入 JS、不引入图表库、不发任何请求
- 趋势与对比数据来自 `reports.sqlite3` 的结构化统计列，不额外请求 GitHub

#### 飞书群消息只读汇总（v2.3 新增）

- 通过**企业自建应用**（`tenant_access_token`）读取配置里指定群的会话历史，产出每个群的"消息条数 + 去重发言人数"
- 只统计真人发言的普通消息，跳过应用/机器人发言与系统消息；窗口与日报采集窗口一致
- 群汇总作为**团队级**一行写入日报头部（`- 飞书群：群名 N 条 · M 人发言`），数据源徽章多一条"飞书消息 N 条"（N 为消息总条数）
- 消息正文在采集器里就地丢弃：不进数据模型、不进 SQLite、不进 Markdown/HTML、不进日志
- 该数据源默认关闭；启用后才出现在采集计划里，未启用时程序行为与 v2.2 完全一致

#### 飞书任务状态同步（v2.4 新增）

- 通过**企业自建应用**（与飞书群消息共用同一套 `app_id` / `app_secret`）只读拉取飞书工作台任务的**当前状态快照**
- 每个任务映射为三态之一：**已完成**（`completed_at` 非空且不为 0）、**未开始**（未完成且配置的开始时间在未来）、**进行中**（其余未完成任务；未返回开始时间字段时一律归入此类）
- 展示位置：当日日报「任务进展」板块内新增子小节「任务进展 · 飞书任务」，排在 GitHub Issue 流转行之后；小节首行给出快照时间与三态计数，随后逐条列出 `状态 · 标题（截止日期）`
- 排序与数量：进行中 → 未开始 → 已完成，同组按截止日期升序（无截止排最后），最多列 20 条，超出显示"其余 N 条见飞书任务"
- 该数据源默认关闭；未启用时连小节标题都不出现，程序行为与 v2.3 完全一致
- 只读取任务标题、状态与截止时间：任务描述不进数据模型、不进产物、不进日志；**不对飞书任务做任何写操作**
- 本期不做定时刷新：任务状态取"生成日报那一刻"的快照，标题里显式标注快照时间；补跑历史日期时额外标注「补跑快照」

#### 管理摘要（v2.8 新增）

- 在成员四板块之前输出团队级「管理摘要」，邮件、站点详情页与飞书卡片共用同一份 Markdown/视图内容
- **今日概览**：飞书任务按 `已完成 / 进行中 / 未开始 / 逾期` 汇总；GitHub 活动汇总提交数、增删行数、涉及文件数、Issue 完成/推进数与互动数；重点进展最多列 3 条，优先当天完成的飞书任务、完成的 GitHub Issue，再选代码提交
- **需要关注**：列出已逾期、当天到期、未来 3 天内到期的未完成飞书任务（按截止日期升序，最多 5 条），并列出所有采集失败的数据源；无风险且数据源正常时显示明确的正常提示
- **下一步**：从进行中和未开始任务中选最多 3 条，进行中优先，其次按截止日期升序；已经在「需要关注」出现的任务不重复
- 新增可选配置 `report.public_base_url`：非空时生成 `daily-report-YYYY-MM-DD.html` 在线日报链接，邮件显示按钮、飞书卡片显示 Markdown 链接；为空时两处都不出现，网页本身不重复显示入口
- 管理摘要只消费本次采集已有数据，不新增 API 请求、不调用外部模型；历史日报不回填

#### 数据来源标注（v2.4 新增）

- 在所有**对外**产物末尾追加一行统一格式的标注，三要素固定顺序：`数据来源：<各数据源全称> ｜ 采集时间：YYYY-MM-DD HH:MM（时区） ｜ 授权范围：<配置值>`
- 覆盖范围：邮件正文（纯文本部分与 HTML 部分）、飞书群卡片、站点日报详情页、站点索引页页脚
- 数据源全称按本次**实际参与采集**的数据源动态生成（如 `GitHub 仓库 owner/repo`、`飞书群 群名`、`飞书任务`），未启用的源不出现
- 授权使用范围默认写「仅限团队内部日报展示」，可在配置里改成与实际约定一致的口径；标注可整体关闭
- 飞书卡片正文超长被截断时，标注行必须保留在末尾，不得被截掉

#### 工时统计（v1.1 新增；v2.7 口径扩展）

- 从成员当日的 **GitHub 活动时间**推导工时，采用**会话法**。活动分三类：提交（按 `author`）、Issue 状态变更（按 `assignee`，取该次变更发生的时刻）、评论（按 `sender`）；三类时间戳合成**一条活动流**，相邻活动间隔超过阈值（默认 60 分钟）即切分为新的工作段；每段时长 = 末次活动 − 首次活动 + 收尾时长（默认 0.5h）；只有一条活动的工作段按 0.5h 计
- 按自然日（配置时区）分组计算，逐日封顶（默认 12h）并按固定网格四舍五入（默认 0.5h），再汇总为窗口内合计
- 日报新增"工时统计"板块，位置为**任务进展之后、协作沟通之前**，每位成员显示 `工时：2.5h（提交 1 · 任务 1 · 评论 1，1 个工作段）`，**只列非零类别**
- 日报头部显示团队合计与人均，并标注口径："按提交/任务/评论时间推导，非真实考勤"
- 成员当日无任何活动显示 `0h（今日无记录）`；**三个活动数据源全部失败**时才显示 `工时数据不可用（原因）`（v2.7 放宽：单个源失败不再作废整块工时，失败的数据源由头部徽章显式标注）
- 口径变更**不回溯**：历史已生成的日报保持旧口径数字，"近 N 期"与"对比上期"会出现一次性跳变（属于口径变更的必然结果，已在 README 与 design.md 说明）

#### 静态日报站

- 生成 `docs/index.html` 索引页（列出历史日报：日期、成员数、生成时间）与 `docs/daily-report-YYYY-MM-DD.html` 详情页
- 站点为纯静态页面：无后端、无登录，移动端可读
- 通过 GitHub Pages（main 分支 `/docs` 目录）发布，供干系人只读浏览
- 移动端可读性（v2.4）：正文大标题只放"<团队名> 智能日报"，日期移到头部信息行，不再在窄屏被折成两行；头部信息拆成"日期 / 团队 / 生成时间"与"工时"两行
- 空板块合并（v2.4）：同一份日报里内容板块（代码提交 / 任务进展 / 协作沟通）为空的数量 ≥ 2 时合并成标题「部分板块无记录」+ 正文 `板块 A、板块 B`；工时统计与飞书任务各自带口径，不参与合并
- 提交行两行布局（v2.4）：HTML 侧每条提交渲染为"主行（仓库 + 提交信息）+ 元信息行（短 SHA 链接 · 变更统计）"，避免一条提交折成三行；Markdown 与飞书卡片仍保持单行形态

#### 浏览器端日报工作台（v2.0 新增）

- 索引页内联一个"日报工作台"：填写日报日期、今日完成（必填）、明日计划、需要协助，点"生成日报"拼出一份 Markdown 日报
- 手写日报固定格式：`# 工作日报 · YYYY-MM-DD` + `## 今日完成 / ## 明日计划 / ## 需要协助`；空小节写 `- 未填写`，不替用户猜测
- 编辑框内容可自由修改；"复制日报"按钮把内容写入剪贴板（https / localhost 用 Clipboard API，其他环境退回 `document.execCommand`，都失败则选中内容并提示手动复制）
- 生成的草稿自动存入**浏览器本地存储**（localStorage），支持载入、复制、删除单条与清空全部；同一日期重复生成会覆盖旧记录，最多保留 50 条
- 工作台提供"从自动日报载入"下拉：选定日期后把该期自动日报的 Markdown 填进编辑框，改完再复制或存为本地草稿
- 日报详情页提供"复制 Markdown"与"载入到工作台"两个按钮（后者通过本机存储中转后跳回索引页工作台）
- 渐进增强：工作台区块默认隐藏，脚本就绪后显示；浏览器禁用脚本或本地存储不可用时，页面仍然是一份可正常阅读的只读日报站
- 页面全程不联网：不请求 GitHub、不写回仓库、不触发飞书与邮件推送

#### 推送通知

- 每个工作日 18:00 由 Cron / 计划任务自动触发日报生成流程
- 通过 SMTP 服务向团队 Leader 发送 HTML 格式日报
- 通过飞书**群机器人 Webhook**（自定义机器人）将 Markdown 格式日报推送至团队群组，无需创建企业自建应用、无需申请任何飞书开放平台权限
- 支持飞书机器人的三种安全设置：**签名校验**（配置 `notify.lark_bot.secret`）、自定义关键词（建议填「日报」）、IP 白名单
- 提供 `python main.py --test-lark` 自检命令：只发一条纯文本自检消息，不采集、不生成日报、不发邮件，用于在正式推送前确认通道可用

### 2.2 不做什么（本期明确排除）

- 不做智能摘要和 AI 总结（本期只做数据清洗与规则过滤，不涉及语义理解）
- 不做常驻 Web 服务和登录权限体系（日报站是静态页面，不接受写操作）
- 不新增任何服务端接口或后端服务（v2.0 的工作台交互全部在浏览器本地完成）
- 不把手写草稿写回 GitHub、不推送到飞书或邮箱、不写入 SQLite（草稿只存在使用者本机浏览器，v2.0 明确排除）
- 不做跨设备/跨浏览器的草稿同步，不做账号体系（v2.0 明确排除）
- 不做移动端 App
- 不做历史日报的全文搜索（索引页保留"列表 + 近 N 期趋势"：v2.3 起提供提交数与工时的内联 SVG 迷你图，仍不做可交互的图表分析与下钻）
- 不做个人日报的手工编辑与补充功能
- 不做支持多团队隔离/多租户架构
- 飞书只接入"群消息汇总"与"任务状态快照"两种数据源：群消息**只统计条数与发言人数**，不把正文写入任何产物或日志（v2.3）；任务**只读状态**，不做任务的新建/修改/完成/删除，不做任务流转历史，不做任务描述与评论的采集（v2.4）。审批、云文档、单聊、日历仍不作为数据源
- 不做飞书私聊/单聊推送、不做飞书审批或群管理；**推送**仍只用群自定义机器人 Webhook（只写通道），**读取**另用只读的企业自建应用（v2.3）
- 不做飞书任务的定时刷新与常驻同步（v2.4 明确排除）：任务状态只在生成日报时取一次快照，不注册计划任务、不做后台轮询、不做增量同步；想看最新状态就重跑一次日报
- 不接入考勤/打卡数据源，不做人工填报工时（工时一律由 GitHub 活动时间推导，v1.1 明确排除、v2.7 明确活动范围）
- 不做精确到分钟的工时统计（工时以 0.5h 为最小网格）
- 不做工时与考核挂钩的任何计算；工时趋势只做"近 N 期迷你图"与"较上期差值"两种展示（v2.3）

### 2.3 技术约束

- 开发语言：Python 3.11 及更高版本
- 运行环境：本机或内网服务器，Docker 容器化部署为可选项
- 外部依赖：GitHub REST API（可选 Token）、公司邮件服务（SMTP）、飞书群机器人 Webhook、飞书开放平台（企业自建应用：群消息与任务只读接口，v2.3/v2.4）
- 运行方式：基于 Cron / Windows 计划任务的定时任务，不需要常驻后台服务
- 数据存储：本地 SQLite（仅用于存储日报历史记录，不部署远程数据库）
- 静态站发布：GitHub Pages 直接发布 `docs/` 目录，不引入 CI 服务与密钥

### 3.3 边界场景

- [ ] 若团队成员当日无任何提交、任务或评论，日报对应板块应显示"今日无记录"

- [ ] GitHub API 超时时应重试（上限三次，间隔 5s），仍失败则标记该数据源失败
- [ ] 系统需要识别非工作日（周末及配置的节假日），并自动跳过日报生成
- [ ] 所有数据源全部失败时，不生成空日报，只记录错误日志
- [ ] 成员当日无活动时，工时显示 `0h（今日无记录）`；只有三个活动源**全部**失败时才显示 `工时数据不可用（原因）`（v2.7 放宽）
- [ ] 三类活动（提交 / Issue 状态变更 / 评论）都能推进工时：只有评论、只有任务也得出非 0 结果（v2.7）
- [ ] 单人单日工时不得超过配置上限（默认 12h），且结果落在 0.5h 网格上（v1.1）
- [ ] 未配置飞书 Webhook 时执行 `--test-lark` 应立刻提示缺哪个变量，不发起网络请求；飞书推送失败（含签名不匹配、关键词不匹配）只记录日志并返回失败，不影响日报生成与站点渲染（v1.2）
- [ ] 浏览器禁用 JavaScript 时，站点页面仍可正常阅读，工作台区块不显示、不报错（渐进增强，v2.0）
- [ ] 浏览器禁用本地存储（隐私模式）时，工作台仍可生成与复制，但明确提示"草稿只在本次会话内有效"（v2.0）
- [ ] 剪贴板权限被拒绝时，应退化为选中内容并提示用户手动复制，页面不报错（v2.0）
- [ ] 本地草稿最多保留 50 条；同一日期重复生成覆盖旧记录而非新增（v2.0）
- [ ] 手写内容与日报正文一律以纯文本方式渲染，含 `<script>` 等标签的输入不得在页面上执行（v2.0）
- [ ] 飞书任务接口未授权（错误码 99991672）时，既不阻断其它数据源，也不把原始报文塞进日报，而是给出"补 `task:task:read` / `task:tasklist:read` 权限并重新发布"的提示（v2.4）
- [ ] 飞书工作台任务清单为空时，该小节显示"飞书工作台暂无任务"，而不是"数据获取失败"（v2.4）

- [ ] 补跑历史日期时，飞书任务小节标题带「补跑快照」，避免被读成当天发生的流转（v2.4）

## 4. 术语定义

| 术语 | 定义 |
| --- | --- |
| 日报 | 系统自动生成的每日工作摘要，涵盖代码、任务、沟通三个维度 |
| 成员 | 已在配置文件中完成 GitHub 账号/邮箱映射绑定的团队成员 |
| 数据源 | 提供原始工作数据的采集单元（本期为 GitHub Commit、GitHub Issue、GitHub 讨论、飞书群消息、飞书任务五类） |
| 采集窗口 | 单次采集所覆盖的时间跨度，默认为配置时区当日 00:00 至任务执行时刻 |
| 任务进展 | 由 GitHub Issue 状态流转（新建 / 进行中 / 已完成）推导出的任务变更记录；v2.4 起同一板块还包含飞书任务的当前状态快照 |
| 飞书任务快照 | 在生成日报那一刻读到的飞书工作台任务状态（已完成 / 进行中 / 未开始），不是任务流转历史；不做定时刷新（v2.4） |
| 数据来源标注 | 对外产物（邮件 / 飞书卡片 / 站点页面）末尾统一追加的一行溯源信息，三要素为数据源全称、采集时间、授权使用范围（v2.4） |
| 授权使用范围 | 数据来源标注的第三要素，声明这份数据允许被用在什么范围，默认"仅限团队内部日报展示"，由配置决定（v2.4） |
| 协作沟通 | 由 GitHub PR 评审评论与 Issue 评论按关键词筛选出的讨论记录 |
| 部分失败 | 至少一个数据源成功、另一个失败；应生成带"数据获取失败"标注的日报 |
| 静态日报站 | 由 `docs/` 目录下的 HTML/CSS 组成的只读站点，通过 GitHub Pages 发布 |
| 工时 | 由成员当日 GitHub 活动时间（提交 / Issue 状态变更 / 评论）推导出的工作时长，单位为小时，网格为 0.5h（v1.1；v2.7 扩展活动范围） |
| 工作段 | 会话法中一段连续的提交活动：相邻提交间隔不超过阈值的提交归为同一段（v1.1） |
| 推导工时 | 明确区别于考勤工时：由提交行为间接推算，仅用于观察工作节奏，不作为考核依据（v1.1） |
| 群机器人 Webhook | 飞书群内"自定义机器人"提供的只写 HTTP 地址（形如 `https://open.feishu.cn/open-apis/bot/v2/hook/xxxx`），无需鉴权流程即可向该群推消息（v1.2） |
| 签名校验 | 飞书机器人可选的安全设置：请求需附带 `timestamp` 与按官方算法（HMAC-SHA256 后 Base64）算出的 `sign`，否则返回 19021 错误（v1.2） |
| 工作台 | 静态日报站页面内的一段浏览器端交互区：填写 → 生成 → 复制 → 本地存草稿，无后端参与（v2.0） |
| 本地草稿 | 存在使用者浏览器 localStorage 里的手写日报记录，只对本机该浏览器可见，不进入仓库、数据库与推送（v2.0） |
| 渐进增强 | 页面在脚本或本地存储不可用时仍保持可读、可用，额外能力只在环境支持时才出现（v2.0） |
